# Integrating against PunchOut Sandbox

You are building the **buyer** side of a punchout — a procurement system that
needs to talk to a supplier — and you have no supplier to talk to. This is one.

`https://punchoutsandbox.com` is a live cXML and OCI supplier. Not a mock: it
validates every document against Ariba's real DTDs, keeps what you send
verbatim, and pushes fulfilment documents back to a URL you nominate.

**Everything here works headlessly.** No browser, no forms, no human. If you are
an agent or a CI job, start at §1 and ignore the website entirely.

> **Which document is canonical.** This file is the quick start. The
> [full documentation](https://punchoutsandbox.com/docs) goes deeper and is
> updated with the service — where the two disagree, believe the site.

## 1. Get credentials

```bash
curl -sX POST https://punchoutsandbox.com/api/signup \
     -d '{"email":"you@company.com"}'
```

Returns an identity, a shared secret, and a map of where each one goes. Free,
instant, no password, no confirmation email. The email is not verified — it is
how you get told if something you depend on changes.

```bash
export PS_AUTH="-H X-Sandbox-Identity:PSB... -H X-Sandbox-Secret:..."
```

HTTP Basic works too, with the identity as the username.

Check the endpoint is reachable — this should answer `401` with a sentence
telling you what to fix:

```bash
curl -s -X POST https://punchoutsandbox.com/punchout/setup -d '<cXML/>'
```

## 2. The JSON API

| Endpoint | Returns |
|---|---|
| `POST /api/signup` | Credentials. `201`. |
| `POST /api/validate` | The full conformance report — every error with its line, element and hint. |
| `POST /api/ingest` | What each buyer platform would do to a cart. |

Send the document as a raw body or as `{"document": "<cXML…"}`.

```bash
curl -sX POST https://punchoutsandbox.com/api/validate $PS_AUTH \
     --data-binary @order.xml | jq '.findings[] | select(.severity=="error")'
```

```json
{ "severity": "error", "line": 10, "element": "Address",
  "message": "<Address> has the wrong children. Expected: Name , PostalAddress? …" }
```

Errors and advisories are kept apart, and the distinction is the point:

- an **error** comes from the DTD. It is mechanical, and your document is wrong.
- an **advisory** is legal cXML that will still cause you trouble on a real
  buyer platform. It is judgement, and it is labelled as such.

Quota is **per account**: 500/day with credentials, 25/day without. If you are
being rate limited while holding credentials, you are not sending them.

## 3. Worked examples

```bash
curl https://punchoutsandbox.com/samples/shipnoticerequest
```

`punchoutsetuprequest` · `punchoutordermessage` · `confirmationrequest` ·
`shipnoticerequest` · `invoicedetailrequest`

Every sample is generated by the same builder that produces the real document,
so it cannot drift out of date, and the test suite asserts each one validates
against the real DTD.

**Read the ship notice before writing an extractor.** `ItemID` is *optional*
there and `UnitOfMeasure` is *not* — the reverse of every other item block in
cXML, and the usual reason a parser written from the other documents fails on
that one. `ShipControl` is also a *sibling* of `ShipNoticePortion` rather than
inside it, because one shipment can cover several orders.

### Then the ones designed to break your parser

Every sample above agrees with itself — the ship notice despatches exactly what
was ordered, in the same unit, at the same price. An extractor that ignores
`UnitOfMeasure` entirely passes all of them. These do not:

| Sample | What it breaks |
|---|---|
| `shipnoticerequest-unit-change` | Ordered 1 BX, despatched 30 EA. No unit field → you read 30 and believe 30 boxes arrived. |
| `shipnoticerequest-partial` | One of three. Marking the line complete closes an order two thirds outstanding. |
| `confirmationrequest-price-change` | Accepted at a higher price. Assuming confirmations are acceptances means the invoice tells you. |
| `confirmationrequest-backordered` | Confirmed, and nothing is coming for eight weeks. |
| `invoicedetailrequest-split-line` | One PO line invoiced as two. One-to-one matching drops or double-counts. |
| `punchoutordermessage-quirks` | Every catalogue quirk at once. Survive this and you survive real suppliers. |

All are **conformant cXML that a real supplier really sends**. The point is not
malformed input — `/api/validate` covers that — but well-formed input carrying a
fact your code may be assuming away.

## 4. The four integration points

| # | Direction | Endpoint | Proves |
|---|---|---|---|
| 1 | you → sandbox | `POST /punchout/setup` | Your `PunchOutSetupRequest` is well-formed and your credentials arrive in the elements you intended |
| 2 | sandbox → you | your `BrowserFormPost/URL` | You can parse a `PunchOutOrderMessage` |
| 3 | you → sandbox | `POST /order` | Your `OrderRequest` is conformant and internally consistent |
| 4 | sandbox → you | your cXML inbox | You can ingest confirmations, ship notices and invoices |

Points 3 and 4 are the half nobody can normally test, because it needs a
supplier willing to send you real documents.

### The round trip, headless

```bash
curl -s -c jar -b jar -X POST https://punchoutsandbox.com/punchout/setup \
     -H 'content-type: text/xml' --data-binary @setup.xml    # → StartPage URL
curl -s -c jar -b jar "$START_PAGE"                          # sets the session cookie
curl -s -c jar -b jar https://punchoutsandbox.com/shop/office.paper
curl -s -c jar -b jar -X POST .../cart/add -d 'sku=MSC-1001&quantity=3'
curl -s -c jar -b jar -X POST .../cart/return -d 'mode=cart' # → cxml-base64 field
```

Base64-decode the `cxml-base64` field and you have the cart.

A live punchout session is authorisation on its own — the storefront never asks
the shopper to sign up, because they are your employee and you authenticated on
their behalf. `/shop` is a department index; products live in leaf categories
with dotted ids like `office.paper`.

### Receiving documents

Set your cXML inbox at `/settings`, then generate a confirmation, ship notice or
invoice against an order and send it. You will see exactly what you replied
with, including whether it was conformant cXML or an HTML error page.

Your endpoint must be **public HTTPS on port 443 with a valid certificate**.
Private addresses, loopback, other ports, plain http, self-signed certificates
and redirects are all refused — this service will not be used as a request
proxy. A staging URL or a tunnel works; `localhost` does not.

## 5. Five things that otherwise cost an afternoon

**Answer cXML with HTTP 200, even when you reject.** The spec treats any reply
without valid cXML as a *transport* error, which suppliers retry ten times,
hourly. A helpful `400` turns a clean refusal into an all-day retry storm. Put
the refusal in a cXML `Status` code inside a 200.

**cXML forbids the `Z` timestamp designator.** `utcnow().isoformat() + "Z"` is
probably the most violated rule in the standard. Use a numeric offset.

**Echo `BuyerCookie` unchanged.** You mint it; it is the only thing binding a
returned cart to the requisition that opened it.

**`ItemOut/@lineNumber` is optional in the DTD and mandatory in practice.**
Confirmations, ship notices and invoices all reference lines *by number*.

**Read the `Status` text, not just the code.** It reports which element your
credentials arrived in, whether your header `Total` reconciles with the sum of
your lines, and how many errors you have. That text lands in your own
transaction log, which is where you will actually look at 2am.

## 6. What a schema check cannot tell you

cXML imposes almost no length limits. Every limit that truncates your data is
imposed by the **buyer platform**, on ingestion, and none of them publish it. So
a perfectly valid cart can arrive with the wrong price on it.

`POST /api/ingest` — or [`/ingest`](https://punchoutsandbox.com/ingest) — applies
what each platform is known to do. The same valid cart:

- **SAP Ariba** shows 255 characters on the PO, counted in *bytes*, so a
  Japanese description runs out around 666 characters; `?` `{` `}` in a part ID
  are a hard reject
- **JAGGAER** silently rewrites an unrecognised `UnitOfMeasure` to `EA` — a box
  of 30 at £9.99 becomes 30 each at £9.99, and the buyer computes £299.70
- **Coupa** fails the import outright for that same unit
- **Oracle** commonly wants `EACH` where everyone else says `EA`

Findings are labelled *reject loudly*, *reject vaguely*, **accept and corrupt**,
or *accept and preserve*. Only the third should worry you: a rejection is a bad
afternoon, a silent change is a wrong price nobody notices until reconciliation.

Rules that are inferred rather than documented are marked `verified: false`,
because a confident wrong answer about your purchase order is worse than an
uncertain one. Full working:
[the conformance reference](https://punchoutsandbox.com/reference/platform-conformance).

## 7. Limits and honesty

| | |
|---|---|
| Sessions | 1 hour |
| Orders | 7 days |
| Documents you submit | Not stored beyond that, and not looked at |
| Cost | £0, with no paid tier |
| SLA | None. It is a sandbox. |

The catalogue is synthetic and every company in it is invented. Some products
are **deliberately quirky** — a unit of measure that will not map, a part number
with leading zeros — because those are the ones that break integrations.

Found something wrong? [Say so](https://punchoutsandbox.com/contact). The most
useful report is a platform limit this has got wrong, or a document it judged
wrongly — being confidently wrong is the one failure mode a validator cannot
afford.
